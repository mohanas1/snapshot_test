Parallel Mode Guide

sequential

One flow finishes before the next starts. Flows are processed one at a time in order.

Use Case: Testing basic connectivity, debugging flow injection, or when you need deterministic execution order.
Example with 4 VMs:
Flow 1: VM-A → VM-B:80 (completes)
Flow 2: VM-C → VM-D:443 (starts after Flow 1)
Flow 3: VM-A → VM-C:22 (starts after Flow 2)
→ One flow at a time, no parallelism

same_vm

One source and one destination VM, but multiple ports simultaneously. Flows sharing the same VM pair execute in parallel.

Use Case: Testing multiple services on the same connection path (e.g., HTTP, HTTPS, SSH from one web server to one database).
Example: VM-A sending to VM-B
Wave 1 (parallel):
  • VM-A → VM-B:80
  • VM-A → VM-B:443
  • VM-A → VM-B:22
  • VM-A → VM-B:3306
→ All ports between same VM pair run together

unique_vms

Each running flow uses two VMs that no other flow is using. Ensures VM isolation across parallel flows.

Use Case: Load testing where you want to ensure no VM is handling multiple flows concurrently (avoids resource contention).
Example with 8 VMs:
Wave 1 (parallel):
  • VM-A → VM-B:80
  • VM-C → VM-D:443
  • VM-E → VM-F:22
Wave 2 (after Wave 1 completes):
  • VM-A → VM-C:80 (VM-A reused)
  • VM-G → VM-H:443 (new VMs)
→ No VM appears in multiple concurrent flows

fan_out

One source sends to several destinations at once. Each source VM fans out to multiple targets in parallel.

Use Case: Simulating a load balancer, API gateway, or service mesh where one frontend distributes to many backends.
Example: VM-A as source
Wave 1 (parallel from VM-A):
  • VM-A → VM-B:80
  • VM-A → VM-C:80
  • VM-A → VM-D:80
  • VM-A → VM-E:80
→ Single source broadcasts to many destinations

fan_in

Several sources send to one destination at once, each on its own port. Many VMs converge to a single target.

Use Case: Simulating many clients hitting one database/API server, or testing destination VM under load.
Example: VM-D as destination
Wave 1 (parallel to VM-D):
  • VM-A → VM-D:8001
  • VM-B → VM-D:8002
  • VM-C → VM-D:8003
  • VM-E → VM-D:8004
→ Multiple sources converge to single destination (different ports)

spread

Any flows run at once; a VM may be in more than one flow. Maximum parallelism with no restrictions.

Use Case: Stress testing, chaos engineering, simulating production-like traffic where VMs communicate freely.
Example chaos:
All parallel (no restrictions):
  • VM-A → VM-B:80
  • VM-A → VM-C:443 (VM-A in 2 flows)
  • VM-D → VM-A:22 (VM-A as dest too)
  • VM-B → VM-C:3306 (VM-B and VM-C reused)
→ No limits, VMs can be source/dest in multiple flows

first_to_all Pattern Locked: 1:all

First IP in your selection sends every configured port to every other VM. One source floods all destinations.

Use Case: Testing monitoring/visibility when a single compromised host scans your entire network.
Example with 5 VMs [VM-A, VM-B, VM-C, VM-D, VM-E]:
VM-A is source (first in list)
Parallel waves:
  • VM-A → VM-B:80, VM-A → VM-B:443
  • VM-A → VM-C:80, VM-A → VM-C:443
  • VM-A → VM-D:80, VM-A → VM-D:443
  • VM-A → VM-E:80, VM-A → VM-E:443
→ First VM sends to all others across all ports

all_to_first Pattern Locked: all:1

Every other VM sends every configured port to the first IP. All sources target one destination.

Use Case: Testing a central collector/aggregator, or simulating DDoS-like traffic to one target.
Example with 5 VMs [VM-A, VM-B, VM-C, VM-D, VM-E]:
VM-A is destination (first in list)
Parallel waves:
  • VM-B → VM-A:80, VM-B → VM-A:443
  • VM-C → VM-A:80, VM-C → VM-A:443
  • VM-D → VM-A:80, VM-D → VM-A:443
  • VM-E → VM-A:80, VM-E → VM-A:443
→ All VMs converge to first VM across all ports

randomized_mesh Chaos Mode

Randomly selects source and destination pairs across the entire selected VM inventory to simulate dense, unstructured east-west traffic storms.

Use Case: Security policy boundary testing, chaos engineering, simulating unpredictable microservices communication patterns.
Example with 6 VMs (randomized):
Shuffled flow order (unpredictable):
  • VM-D → VM-A:80
  • VM-B → VM-F:443
  • VM-E → VM-C:22
  • VM-A → VM-D:3306
  • VM-C → VM-B:53
→ Random pairings simulate chaotic traffic patterns

client_server_pair Tiered Mode

Splits selected VMs into two explicit pools (e.g., frontend vs. backend tiers) and enforces strict one-way communication from tier 1 to tier 2.

Use Case: Validating specific microsegmentation rules, testing firewall policies between network tiers.
Example with 8 VMs:
Clients (first half): VM-A, VM-B, VM-C, VM-D
Servers (second half): VM-E, VM-F, VM-G, VM-H
Allowed flows (clients → servers only):
  • VM-A → VM-E:80
  • VM-B → VM-F:443
  • VM-C → VM-G:22
Blocked: VM-E → VM-A (reverse direction filtered)
→ One-way communication enforced between tiers

port_scan_burst Security/IDS Test

Cycles a single source IP through a wide sequential range of destination ports against a target host to test IPFIX log aggregation throughput and high-frequency alert triggers.

Use Case: Testing IDS/IPS detection, validating security monitoring tools, IPFIX collector performance under port scan scenarios.
Example: VM-A scanning VM-B
Rapid port sweep (parallel batches):
  • VM-A → VM-B:1 (port 1)
  • VM-A → VM-B:2 (port 2)
  • VM-A → VM-B:3 (port 3)
  • ... continues through port range
  • VM-A → VM-B:65535 (last port)
→ Sequential port cycling simulates nmap-style scan
